# Git Commit Messages

Applies whenever the agent generates a commit message, in any repository.

## Voice

- Match the repository's own voice. An engineer wrote it, not an AI.
- No banned words (delve, leverage, utilize, streamline, robust, seamless, comprehensive).
- No filler ("Notably", "Importantly", "It's worth noting").
- No em dashes, zero tolerance. No rhetorical question and answer. No triple-negation reveals.

## Attribution

- Never name the editor, the model, the agent or the assistant in the message body.
- Never add "Generated by" or a tool trailer that the repository has not asked for.
- Where a repository requires an attribution trailer, use exactly the trailer it specifies and
  nothing else.

## Format

- Subject line: imperative mood, lowercase, 72 characters or fewer, no trailing period.
  For example `add db block to config`, `fix webhook idempotency check`.
- Optional body: only when the change needs context the diff does not show (why, trade-off,
  follow-up). One short paragraph, or terse bullets.
- No body for a trivial change (typo, rename, docs nit).
- Scope prefix only when the repository already uses one. Do not invent a new convention.

## What to describe

- The subject answers what changed, in plain words.
- The body answers why it changed, only when that is not obvious from the diff.
- Skip mechanics the diff already shows. Do not write "added 5 lines to config.py".

## Before the first push on a branch

Two checks, both before the first push rather than after. A bump and then a revert leaves two
commits and a review round on the pull request.

**Find the real integration branch.** A `dev` branch existing is not proof that it is the
integration branch, and `origin/HEAD` can point at an abandoned one. Compare the candidates
before basing work:

```bash
git rev-list --left-right --count origin/main...origin/dev
git log -1 --format='%ci %h' origin/dev origin/main
```

Take the live tip, and keep the branch rebased on that tip for the life of the pull request.

**Check how the repository versions.** Some repositories bump a version file per pull request
and some manage versioning centrally, and doing the wrong one either fails a gate or creates a
conflict. Read the base branch rather than assuming:

```bash
git show origin/<base>:.pre-commit-config.yaml   # is a version-bump hook still defined?
git diff origin/<base> -- <version file>         # has this branch already bumped it?
```

If the repository bumps per pull request and the version file is unchanged against the base,
bump the patch number and include it in the same push. If versioning is central, do not bump:
on a conflict, rebase on the base branch and take the base side of every version file. Where a
pre-commit hook claims to bump for you, verify by hand anyway.
